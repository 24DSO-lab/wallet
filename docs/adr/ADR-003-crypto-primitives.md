# ADR-003: Криптографические примитивы

21 ноября 2026 · решение по замечанию 2 из `docs/SECURITY-REVIEW-2026-11-20.md` · статус: принято

## Контекст

Argon2id, blake2b, secp256k1, ripemd160, base58 и BIP32 были написаны в репозитории. Замечание 2 аудита: самописная криптография — лишняя поверхность риска, а `golang.org/x/crypto` (v0.53.0) уже входит в зависимости.

## Решение

| Примитив | Решение | Причина |
| --- | --- | --- |
| Argon2id | Боевой код использует `golang.org/x/crypto/argon2` | Широко проверенная реализация, быстрее (параллельные полосы, SIMD). Результат побайтно совпадает с прежним, формат файла не меняется, существующие кошельки открываются |
| secp256k1 | Остаётся своя реализация | Готовой реализации в `x/crypto` нет. Новая зависимость (например, `btcec`, `go-ethereum/crypto`) тянет за собой большое дерево и не даёт гарантий постоянного времени без cgo. Подпись проверена RFC 6979 и тестами сверки адресов |
| blake2b, ripemd160, base58, BIP32 | Без изменений | Малый объём, закрыты эталонными векторами. `blake2b.go` остаётся только как часть эталонной реализации Argon2id |

Собственный пакет `internal/keystore/argon2id` больше не вызывается из боевого кода. Он оставлен как независимая реализация и защита от регрессий: `compat_test.go` сравнивает его с `x/crypto/argon2` на нескольких наборах параметров, включая несколько полос.

## Компромиссы

- `x/crypto/argon2` не затирает рабочую матрицу памяти после вычисления. Это риск того же класса, что и незатираемые строки пароля в Go; остаточный след в памяти процесса принят, пока кошелёк открыт локально.
- Производные ключи и пароли по-прежнему обрабатываются через `secret.Bytes` и затираются сразу после использования.
- secp256k1 не работает за постоянное время (`math/big`). Это боковой канал для локального наблюдателя.

## Условие для mainnet

Перед включением main-профиля нужен независимый обзор `secp256k1`, RFC 6979 и BIP32 сторонним специалистом. Это добавляется в гейты ADR-001. До тех пор приложение работает только в тестовых сетях.
