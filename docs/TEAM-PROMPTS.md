## 1. Как пользоваться

Каждому разработчику выдаются два блока: общие правила (раздел 3) и его собственный промпт (разделы 4–11). В репозитории сейчас только README и `docs/ADR-001-desktop-wallet.md`, кода нет, поэтому развязка держится на трёх вещах: непересекающиеся каталоги, контракты, замороженные на второй день, и фейки для всего, что ещё не готово.

1. Dev 1 в первый день мерджит PR #0: каркас проекта и контракты. Остальные стартуют сразу по эскизу контрактов из раздела 3 и ребейзятся на PR #0, как только он в `main`.
2. К концу второго дня контракты v0 замораживаются. Дальше любая правка контракта идёт отдельным PR с меткой `contract`.
3. Каждый пишет только в своих каталогах (таблица в разделе 2). Чужой каталог правится только по запросу владельцу.
4. Гейты ADR между этапами проверяют назначенные владельцы (раздел 12).
5. Если вместо людей работают ИИ-агенты, промпты подходят без изменений: каждый агент получает общий блок и свой промпт.

### Допущения сверх ADR

ADR не фиксирует следующие вещи, а без них разработчики разойдутся. Владелец проекта поручил решить их мне (14 ноября 2026), поэтому все девять приняты как есть; любое можно пересмотреть до старта соответствующей зоны.

| № | Допущение | Почему нужно |
| --- | --- | --- |
| A1 | Один Go-модуль, раскладка каталогов из раздела 2 | Иначе нечем разграничить владение |
| A2 | Подпись по дайджестам: адаптер собирает транзакцию и 32-байтные дайджесты, Keystore подписывает их и возвращает подпись вместе с публичным ключом, адаптер собирает итоговую транзакцию. Перед подписью адаптер заново разбирает черновик и сверяет его с намерением пользователя, Keystore сверяет адрес по пути деривации | ADR говорит «подпись только в Keystore» и «поля проверяются локально», но не задаёт форму обмена |
| A3 | Один пароль приложения и один keystore-файл на кошелёк (свои соль и параметры argon2id). Смена пароля перешифровывает все файлы атомарно | ADR не говорит, общий ли пароль у кошельков |
| A4 | Профиль сети (main или test) = отдельный каталог данных: keystore, БД и копии не смешиваются. Для тестовой сети BTC использует coin type 1 (m/84'/1'/0') | ADR даёт пути только для основной сети |
| A5 | Секреты и Wails. ADR требует показать seed при создании и по кнопке «показать seed» и вводить пароль в интерфейсе при каждой отправке, а модель угроз говорит, что методы Wails не принимают и не возвращают seed и пароль. Принято: пароль и парольная фраза идут только внутрь и только в перечисленных методах, seed уходит наружу ровно в двух методах (раздел 3) | Иначе правило из ADR невыполнимо буквально |
| A6 | Таблица `pending_tx` для подписанной транзакции до подтверждения сетью | ADR требует хранить её, но в модели данных её нет |
| A7 | Фейки всех портов и сборка с тегом `mock` у Dev 7 | Dev 8 запускает настоящее приложение без сетей |
| A8 | Xpub: стандартная сериализация BIP32 (xpub и tpub), тип скрипта задаёт код, а не префикс (без zpub) | Dev 2 и Dev 4 должны одинаково читать один и тот же ключ |
| A9 | Межсетевой обмен поставлен на холд (D2): провайдер не выбран, весь этап 4 не разрабатывается, включая обмен ETH и USDC внутри Ethereum | Так записано в открытых вопросах ADR |

### Решения по открытым вопросам ADR

Открытые вопросы ADR закрыты, кроме выбора провайдера обмена: по решению владельца обмен на холде, а ChangeNOW по его сведениям не работает.

| № | Вопрос из ADR | Решение | Основание |
| --- | --- | --- | --- |
| D1 | Wails v2 или v3 | Wails v2.17.0 | На странице [релизов](https://github.com/wailsapp/wails/releases) последняя стабильная v2.17.0, а v3 остаётся бетой (v3.0.0-beta.34, «pre-release software»). Переход на v3 только отдельным ADR |
| D2 | Способ межсетевого обмена | Весь этап обмена на холде, провайдер не выбран. При возобновлении кандидаты: другой обменник по API или THORChain за портом `Exchanger`. Выбор оформляется отдельным ADR, список пар и условия сервиса проверяются заново до начала работы | ChangeNOW по сведениям владельца не работает, провайдера придётся выбирать заново |
| D3 | Доступность сервиса в вашей стране и проверка личности | Снят с повестки вместе с холдом, вернётся при выборе нового провайдера | Актуален только после возобновления обмена |
| D4 | Оценка в фиатной валюте | Не входит в версию 1, нужен отдельный ADR с источником курсов | ADR уже исключает её из первой версии |
| D5 | Провайдеры и бесплатные тарифы | BTC: mempool.space, резерв Blockstream. Ethereum: Alchemy плюс Etherscan. TRON: TronGrid. Лимиты каждый разработчик проверяет на старте и записывает в README своего пакета | Замена провайдера дешёвая, потому что всё идёт за интерфейсом `provider.Client` |

## 3. Общие правила (вставить в начало каждого промпта)

Этот блок одинаков для всех восьми разработчиков: он фиксирует правила ADR, рабочий процесс и эскиз контрактов, от которых зависит параллельная работа. Либо вставьте его целиком перед каждым промптом, либо закоммитьте как `docs/TEAM-RULES.md` и оставьте в промпте ссылку.

### Вводная

Ты один из восьми разработчиков личного некастодиального десктопного кошелька для Windows: Wails + Go + Vue 3 + TypeScript, 1-3 кошелька по 4 актива (BTC, ETH, USDC в Ethereum, USDT в TRON). Источник истины: `docs/ADR-001-desktop-wallet.md`, прочитай его целиком до начала работы. Пиши только в каталогах своей зоны. Если ADR и этот блок расходятся, остановись и спроси, а не выбирай сам.

### Нерушимые правила из ADR

1. Деньги: `big.Int` в минимальных единицах, в БД текстом, никаких `float` и JS-чисел для сумм. Суммы из интерфейса приходят строкой и разбираются в Go.
2. Секреты (seed, ключи, пароль, парольная фраза): отдельные типы без строкового представления, срезы байтов, затирание после использования, никогда в логах и ошибках. Ключи существуют только в Go-процессе.
3. Данные провайдеров API не доверенные: получатель, сумма и комиссия проверяются локально перед подписью.
4. Актив жёстко определяет сеть; адрес проверяется валидатором именно этой сети; сеть подписана на каждом экране.
5. Профиль сети (main или test) один на приложение.
6. Минимум зависимостей. Новая зависимость идёт в PR с обоснованием (зачем, чем плоха стандартная библиотека, размер, поддержка), версии фиксируются в `go.sum` и `package-lock.json`.

### Современные практики

- Go (актуальная стабильная версия, подтверждает Dev 1): `context.Context` первым аргументом, `log/slog`, ошибки с `%w` и проверкой через `errors.Is` и `errors.As`, интерфейсы небольшие, табличные тесты, `go test -race`, фаззинг (`go test -fuzz`) для всех парсеров и валидаторов, `golangci-lint`, `govulncheck`, `go mod verify`. Никаких глобальных переменных с состоянием, зависимости передаются через конструкторы.
- Vue: Vue 3, Composition API, `<script setup lang="ts">`, строгий TypeScript, Pinia, Vue Router, Vite, `vue-tsc`, ESLint (flat config), Vitest, Playwright. Никаких внешних скриптов, шрифтов и CDN, строгий CSP.
- Тесты на известных векторах и записанных ответах провайдеров (`httptest`), а не на живых сетях. Живые тестовые сети нужны только для гейтов.

### Работа в репозитории

- Ветки `dev<N>/<тема>`, trunk-based, squash-merge, ребейз на `main` минимум раз в день, Conventional Commits.
- PR не больше примерно 400 строк (тестовые векторы и сгенерированный код не считаются). Каждый PR проходит CI: сборка, `go vet`, линтер, тесты с `-race`, `govulncheck`, `go mod verify`, для фронтенда `vue-tsc`, ESLint, Vitest.
- `CODEOWNERS` сопоставляет каталоги из раздела 2 владельцам. Чужой каталог правится только по запросу владельцу; если это блокирует работу, делается минимальный PR с его одобрением.
- Контракты (`internal/domain`, `internal/ports`, `app/dto.go`, `frontend/src/api/types.ts`) меняются только отдельным PR с меткой `contract`: маленький, по возможности только добавляющий, объявлен в общем канале до слияния, одобрен владельцами зон, которые контракт используют. Ломающие изменения согласует Dev 1.
- `go.mod` и `go.sum` у всех общие. При конфликте: ребейз и `go mod tidy`, а не ручная правка.
- Пока соседний модуль не готов, работай на фейках из `internal/testkit` (появятся у Dev 7) или на своих заглушках за тем же портом.
- Секретов и реальных API-ключей в репозитории нет; ключи провайдеров приходят из настроек бэкенда.

### Эскиз контрактов

Это ориентир. Точные сигнатуры фиксирует Dev 1 в PR #0, после слияния они обязательны для всех.

```go
// internal/domain
type Asset string   // "BTC", "ETH", "USDC", "USDT"; справочник (сеть, знаки) зашит в коде
type Network string // "bitcoin", "ethereum", "tron"
type Profile string // "main", "test"

type Amount struct{ /* big.Int в минимальных единицах; ParseDecimal(s, decimals), FormatDecimal; в БД и JSON строка */ }

type PublicWallet struct { // только публичные данные
    ID, Name                string
    BTCXpub                 string // xpub или tpub, счёт m/84'/coin'/0'
    ETHAddress, TronAddress string
}

type SendIntent struct { Wallet PublicWallet; Asset Asset; To string; Amount Amount }
type Tx struct{ /* единая запись истории, поля как в таблице transaction из ADR */ }
type Warning  struct { Code WarningCode; Detail string }
type AppError struct { Code ErrorCode; Cause error } // код показывается в интерфейсе
```

```go
// internal/ports
type ChainAdapter interface {
    Network() domain.Network
    ValidateAddress(addr string) error
    AddressFromPublicKey(pub []byte) (string, error) // ETH и TRON
    Refresh(ctx context.Context, w domain.PublicWallet, a domain.Asset) (Snapshot, error) // баланс, история, найденные адреса и UTXO
    Prepare(ctx context.Context, in domain.SendIntent) (Prepared, error) // без ключей: дайджесты, комиссия, описание для экрана, предупреждения
    Verify(p Prepared, in domain.SendIntent) error // сам разбирает байты черновика, не верит полям Prepared
    Finalize(p Prepared, sigs []Signature) (Signed, error)
    Broadcast(ctx context.Context, s Signed) (TxID, error)
    Status(ctx context.Context, id TxID) (TxStatus, error)
}

type DigestRequest struct { Network domain.Network; Path, ExpectedAddress string; Digest [32]byte }
type Signature     struct { Sig [65]byte /* r||s||v */; PubKey []byte /* сжатый */ }
type Secrets       struct { Password, Passphrase secret.Bytes }

type Keystore interface {
    NewMnemonic(words int) (secret.Bytes, error)
    Save(ctx context.Context, id string, mnemonic secret.Bytes, s Secrets) (PublicKeys, error) // создание и импорт
    Verify(ctx context.Context, s Secrets) error
    ChangePassword(ctx context.Context, oldPwd, newPwd secret.Bytes) error // атомарно, все файлы
    RevealSeed(ctx context.Context, id string, s Secrets) (secret.Bytes, error)
    Delete(ctx context.Context, id string, s Secrets) error
    Sign(ctx context.Context, id string, s Secrets, reqs []DigestRequest) ([]Signature, error)
}
```

`Store` содержит по репозиторию на каждую сущность из ADR (wallet, address, balance, utxo, transaction, swap, setting) плюс `pending_tx` и метод `WithTx`. `provider.Client` это тонкий интерфейс над HTTP-клиентом с таймаутами, повторами и резервным адресом: адаптеры получают его в конструкторе и не создают `http.Client` сами.

**Как работает подпись (A2).** Сервис вызывает `Prepare`, затем `Verify`, затем `Keystore.Sign` с дайджестами из `Prepared`, затем `Finalize` и `Broadcast`. Keystore получает функции вида «публичный ключ в адрес сети» при создании (внедрение зависимости, без импорта пакетов адаптеров), выводит ключ по пути, сверяет адрес с `ExpectedAddress` и только потом подписывает.

**Что разрешено пересекать границу Wails (A5).** Пароль и парольная фраза идут внутрь только в `Unlock`, создании и импорте кошелька, `ConfirmSend`, `DeleteWallet`, `RevealSeed`, `ChangePassword`, `RestoreBackup`. Seed идёт наружу только при создании кошелька (один раз) и в `RevealSeed`; внутрь только при импорте. Приватные ключи и xpub не пересекают границу никогда. Фронтенд очищает такие поля сразу после ответа.

## 5. Промпт Dev 2: keystore и HD-деривация

Ты Dev 2. Твой код единственный, кто видит seed и приватные ключи, поэтому здесь самая высокая цена ошибки: меньше кода, больше тестов, никаких «потом доделаю».

**Владеешь:** `internal/secret` (после PR #0 Dev 1), `internal/hd`, `internal/keystore`.

**Не трогаешь:** контракты (меняются только через PR с меткой `contract`), адаптеры, БД.

### `internal/hd`

- BIP39: генерация 12 или 24 слов из `crypto/rand`, проверка контрольной суммы, подсказки слов по префиксу (для мастера импорта), seed с необязательной парольной фразой.
- BIP32/BIP44/BIP84. Пути по ADR: BTC `m/84'/{0 или 1}'/0'` (1 для тестового профиля, A4), ETH и USDC `m/44'/60'/0'/0/0`, TRON `m/44'/195'/0'/0/0`.

- Секреты, которые выводит этот пакет, возвращаются как `secret.Bytes` и затираются вызывающим.

### `internal/keystore`

- Формат файла с версией: параметры argon2id (время, память, потоки, соль) хранятся в заголовке, AES-256-GCM, заголовок включён в AAD, чтобы подмена параметров ломала расшифровку. Параметры калибруются под машину (ориентир 0,5-1 секунда), нижняя граница по рекомендациям OWASP для argon2id; предусмотри усиление параметров при следующей записи.
- Запись атомарная: временный файл, `fsync`, переименование, права только владельцу.
- Один файл на кошелёк, один пароль приложения (A3). `ChangePassword` перешифровывает все файлы атомарно: сначала новые во временный каталог, потом замена, при ошибке откат.
- Методы порта `Keystore` из раздела 3. `Sign` подписывает 32-байтные дайджесты secp256k1 и возвращает 65-байтную подпись `r||s||v` с канонической `s` и сжатый публичный ключ. До подписи для каждого запроса выводит ключ по пути, превращает его в адрес функцией сети, переданной в конструктор, и сверяет с `ExpectedAddress`; при несовпадении подпись отменяется. Буферы затираются через `defer`.
- Парольная фраза BIP39 нигде не сохраняется: не в файле, не в логе, не в ошибке.
- Библиотеки: минимальный набор для secp256k1 и BIP32 (кандидаты: `btcsuite/btcd/btcutil/hdkeychain`, `decred/dcrd/dcrec/secp256k1`, `golang.org/x/crypto/argon2`), выбор с обоснованием в PR.

### Тесты

- Официальные векторы BIP39, BIP32 и BIP84; известные адреса BTC, ETH и TRON для общепринятой тестовой фразы из слов «abandon … about», с парольной фразой и без.

## 7. Промпт Dev 4: адаптер Bitcoin

Ты Dev 4. Ты реализуешь `ports.ChainAdapter` для Bitcoin: адреса из xpub, балансы, история, сборка и проверка транзакции. Ключей у тебя нет и быть не должно: подпись делает Keystore по дайджестам, которые ты ему отдаёшь.

**Не трогаешь:** `internal/hd` (формат xpub согласуй с Dev 2 в первый день), `provider` (Dev 1), `keystore` (Dev 2).

### Что сделать

1. Клиент Esplora (mempool.space или Blockstream; проверь условия и лимиты на старте) за маленьким внутренним интерфейсом, чтобы тесты шли на записанных ответах. Все вызовы через `provider.Client`. Выбор UTXO детерминированный и покрыт тестами на известных примерах; сдача на следующий адрес цепочки сдачи; порог пыли (для P2WPKH 294 сат) даёт предупреждение. 6. `Verify`: разбирает байты черновика самостоятельно и сверяет получателя, сумму, комиссию и адрес сдачи с `SendIntent`; комиссия сверх разумного потолка отклоняется. Не доверяй полям `Prepared` и ответам сервера.

8. Валидация адреса: bech32 с контрольной суммой, только для текущего профиля; чужая сеть и устаревшие форматы отклоняются понятной ошибкой.

Каждый метод проверяется на соответствие правилам пересечения границы из раздела 3.

### Сервисы

- Кошельки: создание в два шага (черновик с seed в памяти и проверка нескольких слов, затем пароль и запись в keystore), импорт с показом первых адресов для сверки, переименование, удаление по паролю и имени кошелька, ограничение `MaxWallets` из конфигурации.
- Балансы и история: загрузка по каждому активу независимо, тайм-ауты, ошибка и время последнего обновления на каждую карточку, обновление при старте и по таймеру, события Wails для интерфейса. Баланс комиссионной монеты (ETH для USDC, TRX для USDT) всегда рядом.
- Отправка: `PrepareSend` (валидация, комиссия, предупреждения про новый адрес и собственный адрес) хранит черновик в памяти с ограниченным временем жизни; `ConfirmSend` идёт строго по цепочке `Verify`, `Keystore.Sign`, `Finalize`, запись в `pending_tx` и в историю как ожидающей, `Broadcast`. Повторное нажатие не создаёт дубль.
- Сессия: блокировка по тайм-ауту бездействия с настраиваемым значением, проверка пароля расшифровкой keystore без сохранения результата.
- Резервная копия: оркестрация `backup` (Dev 3) и `Keystore.Verify` (Dev 2).
- Ошибки провайдеров и сетей превращаются в коды `AppError`, а не в тексты.

### Экраны (по таблице ADR)

- Блокировка. Главная: от 1 до 3 карточек, в каждой четыре актива, время обновления и ошибка по каждому активу отдельно. Мастер добавления кошелька: создать (показ фразы, проверка нескольких слов, пароль, необязательная парольная фраза с двойным вводом) и импортировать (подсказки слов приходят из Go, после ввода показываются первые адреса для сверки).
- Кошелёк: активы, балансы, баланс комиссионной монеты рядом с токеном. Получить: адрес, QR-код (маленькая библиотека без сети, зависимость с обоснованием), пометка «только ERC-20 в сети Ethereum» и «только TRC20 в сети TRON». История: единый список, фильтры, статусы, ссылка на обозреватель.

### Правила безопасности для интерфейса

- Seed, пароль и парольная фраза живут только в локальном состоянии компонента: не в Pinia, не в `localStorage`, не в роутере, не в логе. Поля очищаются сразу после ответа и при уходе с экрана, `autocomplete="off"`.
- Seed скрыт по умолчанию, в буфер обмена автоматически не копируется, при блокировке экран очищается.
- Состояние блокировки приходит из Go, интерфейс его только отображает.
- Адрес и сумма на экране подтверждения не сокращаются и не форматируются в сторону округления.

### Тесты

- Vitest и Vue Test Utils: форматирование сумм на границах (0, 1 сатоши, 1 wei, огромные значения), мастер создания, поток отправки, независимые ошибки по активам.
- Playwright на моках: полный сценарий «создал, получил, отправил, посмотрел историю», блокировка по тайм-ауту, тестовый профиль выделен. Проверка доступности с клавиатуры основных потоков.

## 12. Гейты ADR, порядок слияния, этап обмена

Каждый гейт из плана ADR закрывает один назначенный владелец; пока он не закрыт, следующий этап не начинается, а работа внутри этапа идёт параллельно. Результат гейта Dev 7 записывает в `docs/gates/` (дата, версии, ссылки на транзакции).

| Гейт | Критерий из ADR | Кто закрывает | Кто участвует |
| --- | --- | --- | --- |
| 1. Каркас и ключи | Адреса совпадают с тестовыми векторами | Dev 2 | Dev 1 (контракты), Dev 7 (показ в приложении) |
| 2. Балансы и история | Данные совпадают с обозревателем | Dev 7 | Dev 3, Dev 4, Dev 5, Dev 6, Dev 8 |
| 3. Отправка | Каждый актив отправлен в тестовой сети (BTC, ETH, USDC, USDT) | Dev 7 | Dev 4, Dev 5, Dev 6, Dev 2 (подпись) |

| 5. Обкатка | Восстановление из seed на чистой установке, затем рабочие суммы | Dev 2 и Dev 7 | все |

### Порядок слияния

1. Dev 1: PR #0 (каркас, контракты, `internal/secret`), затем PR #1 (CI, `provider`, `logging`, `config`).
2. Параллельно, в любом порядке: Dev 2, Dev 3, Dev 4, Dev 5, Dev 6 в свои каталоги, Dev 7 с фейками и `mock`, Dev 8 со своим слоем моков.
3. Dev 7 подключает настоящие модули по мере готовности. Сначала Keystore и Store (этап 1), затем адаптеры в порядке готовности.
4. Любые изменения контрактов идут отдельными PR с меткой `contract` между этими слияниями, а не внутри больших PR.

### Этап обмена

Весь этап обмена на холде по решению владельца: провайдер не выбран, ничего из обмена не разрабатывается.
